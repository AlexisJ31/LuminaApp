# ADR-004: Modelo de persistencia para ingesta: RawEvent inmutable y Transaction derivada

- **Estado**: Aceptado
- **Fecha**: 2026-10-04
- **Contexto**: Trazabilidad, auditoria y re-procesamiento de transacciones
- **Decisores**: Equipo de Arquitectura de LuminaApp

## Contexto del Problema

Cuando los eventos financieros entrantes se transforman y guardan directamente sobre la tabla final de transacciones, se pierde el payload original recibido del banco o pasarela. Si las reglas de extraccion o categorizacion fallan o se mejoran posteriormente, es imposible re-procesar los eventos historicos ni auditar con exactitud que datos fueron remitidos originalmente por la fuente externa.

## Decision

Se separa la persistencia de ingesta en dos niveles:

1. **`RawEvent` (Evento Crudo Inmutable)**:
   - Almacena el payload integro entrante en formato JSON (`payloadJson`), cabeceras relevantes, fuente externa, hash SHA-256 de la carga util y clave de idempotencia.
   - Es de solo insercion (append-only); nunca se modifica ni elimina tras su creacion.
   - Registra el estado de procesamiento del evento (`PENDING`, `PROCESSED`, `DUPLICATE`, `FAILED`).
2. **`Transaction` (Entidad de Dominio Financiero)**:
   - Es el registro derivado y normalizado con relaciones a `Account`, `Category` y `User`.
   - Mantiene una referencia opcional de clave foranea hacia el `rawEventId` originario.
3. Si se refinan los algoritmos de categorizacion o normalizacion, el sistema permite re-ejecutar el pipeline sobre los `RawEvent` historicos sin requerir reenvios por parte del usuario o de los bancos.

## Consecuencias

### Positivas
- Trazabilidad y no repudio total frente a disputas o discrepancias con notificaciones bancarias.
- Capacidad de re-procesamiento historico seguro.
- Aislamiento de fallos durante la transformacion sin perdida de datos crudos.

### Negativas / Mitigaciones
- Mayor volumen de almacenamiento en base de datos. Se mitiga implementando politicas de archivado o compactacion a largo plazo para payloads antiguos.
