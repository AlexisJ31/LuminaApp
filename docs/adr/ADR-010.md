# ADR-010: Formato estandar de errores de API basado en RFC 7807 (Problem Details)

- **Estado**: Aceptado
- **Fecha**: 2026-10-04
- **Contexto**: Interoperabilidad, diagnostico de clientes API y contratos de error predecibles
- **Decisores**: Equipo de Arquitectura de LuminaApp

## Contexto del Problema

Respuestas de error con estructuras heterogeneas (por ejemplo `{ error: "string" }`, `{ message: "string", err: {} }`, o errores no capturados con stacktraces directos) generan fragilidad en los clientes frontend y adaptadores externos como n8n. Esto complica la visualizacion clara de mensajes al usuario e impide el manejo programmatico de codigos de error especificos (como violaciones de idempotencia o limites de tasa).

## Decision

Se estandariza el formato de respuesta para todos los codigos de estado HTTP 4xx y 5xx conforme a la especificacion **RFC 7807 (Problem Details for HTTP APIs)**:

1. El `Content-Type` de las respuestas de error incluye la cabecera `application/problem+json` (o `application/json` con esquema compatible).
2. Toda respuesta de error contiene los siguientes campos canonicos:
   - `type`: URI o identificador textual que clasifica el tipo de error (ejemplo: `https://lumina.pa/errors/validation-failed`).
   - `title`: Descripcion breve y legible del problema.
   - `status`: Codigo de estado HTTP numerico identico al encabezado HTTP (ejemplo: 400, 401, 404, 409, 422).
   - `detail`: Explicacion detallada y contextual de la causa especifica del fallo.
   - `instance`: Ruta relativa o identificador del recurso que genero el incidente (ejemplo: `/api/v1/transactions/tx-123`).
   - `invalidParams` (opcional en 422/400): Arreglo detallado con los campos que fallaron la validacion de esquema Zod con su nombre y motivo.
   - `code` (opcional): Codigo de negocio interno (ejemplo: `DUPLICATE_IDEMPOTENCY_KEY`, `INSUFFICIENT_FUNDS`).

3. Se implementa un middleware global capturador de excepciones que intercepta cualquier error no controlado y lo traduce a este formato canonico sin filtrar detalles internos de infraestructura al cliente.

## Consecuencias

### Positivas
- Contrato uniforme y completamente predecible para frontend, webhooks externos y clientes de terceros.
- Facilitacion de mensajes de retroalimentacion precisos y amigables para el usuario final en la interfaz.

### Negativas / Mitigaciones
- Requiere adaptar los controladores existentes para utilizar helpers de error estandarizados.
